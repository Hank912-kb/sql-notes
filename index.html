Part 1 · 資料庫設計（講義 Introduction、02–07、Design Patterns、Meta Modeling、Graph Data Models、Physical versus Catalog Classes）

D1. 資料庫系統導論 — 資料、儲存裝置、檔案系統、DBMS

🌍 什麼時候會用到：考題常問「檔案系統有什麼限制、資料庫怎麼解決」、「DBMS 提供哪幾種語言」、「抽象層級由下到上是什麼」。這一章是整門課的地圖：後面每一章都在某一個抽象層級上工作。

D1.1 資料是什麼？

  • 資料（data）是一組質性或量化變數的值；單筆資料是資訊的個別元素，可以被量測、蒐集、報告、分析，再用圖表視覺化。
  • 資料代表「某些已存在的資訊或知識，被編碼成適合使用或處理的形式」。
  • bit 是最小的資料單位，只有 0 / 1 兩種值，可以用兩種狀態的裝置實作；byte = 8 個 bit。

D1.2 電子儲存裝置

類型特性例子
暫時性（揮發性）Transient / volatile要通電才能保存資料，斷電資料立刻消失。RAM 的特性是不管資料放在哪個位置，存取時間幾乎一樣。RAM
永久性（非揮發性）Persistent / nonvolatile建立資料的程式結束、甚至斷電後，資料結構仍能被存取。HDD、SSD、NVM、ODD
裝置重點
HDD 硬碟多片旋轉的磁性碟片（platter）＋可移動的讀寫頭。碟片分成磁軌（track），磁軌分成磁區（sector）；所有碟片上離圓心等距的磁軌合稱一個磁柱（cylinder）。參數：搜尋時間 seek time（移動讀寫臂，約 2–15 ms）、旋轉延遲 rotational latency（約 4 ms）、傳輸時間 transfer time、平均存取時間約 10 ms；相比之下讀 RAM 一個 byte 約 10 ns。操作：讀磁區、寫磁區、移動讀寫頭。
SSD 固態硬碟用 NAND flash，沒有可動零件。隨機存取 < 0.1 ms；讀可達 400 MB/s，寫較慢（要先把位元清成 0 再設 1）。HDD 和 SSD 都是區塊裝置（block device）：用邏輯位址、以固定大小的連續區塊為單位存取。
NVM 非揮發性記憶體Phase-Change RAM、Magnetic RAM、Resistive RAM 等新技術：低耗電、延遲接近 DRAM。特性：可用 byte 定址（不必整塊傳）、寫入吞吐量比 SSD 高一個數量級以上、讀寫不對稱（寫比讀慢，同一格寫太多次會壞）。
ODD 光碟機用雷射讀寫 CD、DVD、Blu-ray。

永久儲存的邏輯模型：一連串固定大小的資料區塊（data block），每塊 2 / 4 / 8 / 16 / 32 KB，用區塊位址識別。

D1.3 檔案系統與它的限制

只有「一串區塊」太陽春，所以把區塊分組成有名字的檔案（file）：檔案是記錄（record）的集合，記錄是欄位（field）的序列，欄位 = [位址, 值]，位址 = 檔名 + 區塊編號 + 區塊內偏移量。檔案定義決定欄位名稱和長度。操作：開檔、關檔、讀寫指定位址的記錄、讀寫下一筆記錄。

STUDENT(number, firstname, lastname, date-of-birth, degree) SUBJECT(code, title, credits) ENROLMENT(student-number, subject-code, enrolment-date, status)

資料相依（程式寫死檔案格式）提供通用查詢語言，可快速寫出臨時（ad-hoc）查詢

D1.4 資料庫系統：概念層與邏輯層

資料庫（database）是一組共享、邏輯相關、為了滿足組織資訊需求而設計的資料；更抽象地說，它是「現實世界某個片段的描述」。

概念層（conceptual）

由物件（object）組成，物件用屬性（attribute）描述，透過關聯（association）彼此連結。例：SUPPLIER —Supplies— PART。畫法：概念綱要（class diagram）或實例圖（instance diagram）。

邏輯層（logical）

常見是表格式（tabular）：資料表＝表頭＋列＋欄。也可能是階層式（hierarchical）（樹）或網狀式（network）（用指標連起來的記錄）。

抽象層級（由下到上）使用的概念
硬體層bit, byte, sector, track, cylinder
實體層byte, data block, sequence of data blocks
檔案層field, address of field, record, file
邏輯層attribute, value, row, column, link, table, hierarchy, network
概念層object, property, value, link, class of objects, association

D1.5 資料庫管理系統 DBMS

DBMS 是讓使用者定義、建立、維護並控制資料庫存取的軟體系統。它提供五種語言：

語言用途層級
DDL — Data Definition Language定義資料庫結構概念 / 邏輯
DML — Data Manipulation Language新增、修改、刪除內容概念 / 邏輯
QL — Query Language查詢內容概念 / 邏輯
ACL — Access Control Language決定不同層級的存取權限概念 / 邏輯
DAL — Database Administration Language管理資料庫邏輯 / 實體

DBMS 相關人員

系統分析師、資料庫設計師、應用程式開發者、資料庫管理員（DBA）、安全管理員、終端使用者。

優點 ／ 缺點

優點：控制冗餘、控制一致性、資料共享、安全性提升、效能提升（不一定）、生產力提升。缺點：複雜、龐大、營運與維護成本、效能、不同系統互不相容、故障代價高。

D2.3 物件建模的基本詞彙

物件建模（object modeling）是一種概念建模：把領域規格轉成簡化的類別圖。原則：資料庫內容被切成一個個離散的物件；物件用屬性（和方法，但這門課忽略方法）描述；物件用某些屬性的值識別；同質的物件組成類別。

「個體」層級（一個）「型別」層級（一群）例子
物件 object類別 class of objects學生 James 是物件；所有學生組成類別 STUDENT
連結 link關聯 association「Peter 供應 bolts 給 James」是 link；SUPPLIER Supplies PART To MANUFACTURER 是 association
屬性值 value屬性 attributestudent number = 1234567

識別子可以是一個屬性（學號），也可以是多個屬性的組合（教室 = 建築編號 + 房號；出貨 = 供應商名 + 日期 + 時間）。

類別 SUPPLIER、PART 和多對多關聯 Supplies。

一般化（generalization）表示類別之間「是子集合」（Is-a-subset）的關係：如果 X 的所有物件都是 Y 的物件，Y 就是 X 的一般化。例：STUDENT 是 UNDERGRADUATE STUDENT 和 POSTGRADUATE STUDENT 的一般化；HUMAN 是 STUDENT 和 LECTURER 的一般化；講義最愛的例子：BAT 是 GREY-BAT、VAMPIRE-BAT、BATMAN 的一般化。

空心三角形指向「上層類別（superclass）」。讀法：UNDERGRADUATE-STUDENT IS-A STUDENT。

D3.2 關聯與多重性 — 怎麼讀數字

  • 兩個類別之間的實線 = 關聯；線上的字是關聯名稱，旁邊的實心小三角形 ▶ ◀ ▲ ▼ 表示閱讀方向：「PERSON Owns VEHICLE」。
  • 多重性寫在線的兩端。讀法口訣：「一個 A 對到幾個 B → 看 B 那一端的數字」。上圖：一個 PERSON 擁有 0..* 台 VEHICLE（看 VEHICLE 那端）；一台 VEHICLE 有 1 個主人（看 PERSON 那端）。
  • 類別和關聯在圖上的位置不影響意思（把 VEHICLE 畫在左邊，意思一樣）。

三種基本類型。注意 COMPANY 端是 0..1：員工可以不屬於任何公司；EMPLOYEE 端是 *：公司可以有 0 個員工。

更多講義例子：一支 TEAM 由 22 個 PLAYER 組成、一個 PLAYER 只屬於一支 TEAM（TEAM 端 1、PLAYER 端 22）；一場 GAME 由 11 個球員加最多 3 個替補上場（PLAYER 端 11..14），一個球員參加 0 或多場（GAME 端 *）。

D3.3 連結屬性（Link attribute）

連結屬性描述的是「關聯本身」，畫成一個標題欄空白的類別框，用虛線接到關聯線上。為什麼 enrolment-date 不能放進 STUDENT 或 SUBJECT？

  • 放 STUDENT（enrolment-date[*]）：知道學生有一堆選課日期，但不知道哪個日期對應哪一科。
  • 放 SUBJECT：知道科目有一堆日期，但不知道是誰選的。
  • 所以日期是貼在「某學生–某科目」那條 link 上的標籤 → 只能是連結屬性。判斷口訣：這個值要同時知道兩邊是誰才有意義 → 放在關聯上。

另一例：SUPPLIER Supplies PART，出貨日期 shipment-date 和數量 quantity 都是連結屬性。

D3.4 關聯類別（Association class）

  • 跟連結屬性很像，但框框有類別名稱（ENROLMENT），代表「這個關聯本身也是一個類別」。
  • 關聯類別可以有自己的識別子（例如 enrolment-number）；多對多關聯的關聯類別有預設識別子 = 兩邊類別識別子的組合 (snumber, code)，不用寫進框框。
  • 什麼時候要用關聯類別而不是連結屬性？當它還要跟別的類別建立關聯時：例如 SHIPMENT（Supplies 的關聯類別）Delivered-to CUSTOMER。

D3.5 限定（Qualification）

  • 房間的識別子是 (bnumber, rnumber)：一個屬性來自 BUILDING、一個來自 ROOM — 跨兩個類別的組合識別子要用限定表示。
  • 限定 = 貼在「一」那端類別旁的小方框，裡面寫屬性名。意思：在某一棟建築裡，給定房號最多只有一間房（所以另一端是 0..1）。
  • rnumber 是 ROOM 的區域識別子（local identifier）：同一棟裡的房號不重複；(bnumber, rnumber) 是 ROOM 的預設識別子。
  • 其他例子：銀行帳號在某家銀行裡唯一（BANK [account#] — ACCOUNT）；校區 → 建築 → 房間可以連續限定；股票代號在某交易所裡唯一（STOCK-EXCHANGE [ticker-symbol] — COMPANY）。

多對多關聯的中段限定：如果學生可能重修同一科（講義說的「悲觀的現實」），(snumber, code) 就不再唯一，識別子變成 (snumber, code, enrolment-date)。畫法是把限定方框放在關聯線中間：

中段限定 ⇔ 左右兩邊各做一次單邊限定。關聯類別的識別子 = 左邊識別子 + 右邊識別子 + 限定屬性。

D3.6 一般化（Generalization）

  • 箭頭從子類別指向上層類別，箭頭是空心三角形；多個子類別的箭頭可以「合併」成一個。
  • 子類別繼承上層的屬性與識別子，只寫自己多出來的屬性。
  • 講義 Design Patterns 裡三角形旁標 (t,e) 或 (p,e)：t = total（每個上層物件都一定屬於某個子類別）、p = partial（可以不屬於任何子類別）；e = exclusive（最多屬於一個子類別）。

D5. 設計模式、名稱的角色、實體類別 vs 型錄類別

🌍 什麼時候會用到：很多建模題其實是同幾種「形狀」反覆出現：樹狀結構、物品 vs 物品描述、區域識別子……認得出模式，就能直接套用正確的畫法。「書 vs 館藏複本」正是你 Assignment 1 的核心問題。

D5.1 具體化（Reification）

具體化 = 把原本不是物件的東西（通常是一個屬性）「升級」成物件。例：員工有技能 → 把 skill[*] 升級成類別 SKILL；學生就讀學位 → 把 degree 升級成類別 DEGREE。之後技能、學位就能有自己的屬性和關聯。邏輯設計第 1 步處理多值屬性時也是用這招（D8）。

D5.2 名稱扮演的角色

同一個名字「sugar」在不同設計裡扮演不同角色，選哪一種會大大影響綱要能不能擴充：

角色設計評語
屬性值STOCK-ITEM(name ID, price, date)，有一列 name = sugar最有彈性：新商品只是多一列
屬性名稱COMMODITIES(sugar, tobacco, wheat, …, date ID)新商品要改綱要（加欄）
類別名稱SUGAR(price, date ID)最僵硬：每種商品一個類別

D5.3 五種設計模式

模式（pattern）是物件模型的一個片段，裡面有一或多個參數，當作類別和關聯的佔位符號；套用時把參數換成實際名稱。

① 簡單樹 Simple tree

樹有一個根；父節點有很多子節點；子節點最多一個父節點 → 一條自我關聯，父端 0..1、子端 *。例：管理結構有一個 CEO，主管有很多下屬；裝置由零件組成，零件最多屬於另一個零件。

② 複雜樹 Complex tree

節點分成葉節點和分支節點（一般化），只有分支節點能有子節點。例：檔案系統 — DATA FILE、DIRECTORY FILE 都 IS-A FILE；目錄包含多個子檔案；檔名是檔案在目錄裡的區域識別子（限定）。

③ 物品描述 Item description

ITEM * —has— 1 ITEM-DESCRIPTION：很多實體物品共用一份描述。例：汽車 — 組裝規格；課程 — 課程描述。就是 D5.4 的「實體 vs 型錄」。

④ 限定 Qualification

某個屬性是區域識別子：房號在建築內唯一、分行名稱在銀行內唯一 → 畫限定。

⑤ 同構 Homomorphism

物品 1 有描述 1、物品 2 有描述 2；物品 1 跟物品 2 有關，描述 1 跟描述 2 也有平行的關係。例：課程描述包含評量規格、課程包含評量；航班描述包含航段描述、航班包含航段。

左：簡單樹（員工管理結構，角色 manager / subordinate）。右：複雜樹（檔案系統，檔名是目錄裡的限定）。

同構模式：上下兩條「consists of」平行。

🌍 什麼時候會用到：邏輯設計的終點就是關聯式綱要；寫 CREATE TABLE 時的 PRIMARY KEY、UNIQUE、FOREIGN KEY、NOT NULL、CHECK，全都對應到這一章的四種一致性限制。正規化（第 23 章）的 superkey / candidate key 定義也在這裡。

D7.1 資料模型與關聯式資料表

資料模型提供資料的抽象觀點（view of data），用來定義、操作、查詢與管理資料。1970 年 IBM 的 E. F. Codd 提出以表格為基礎的關聯式資料模型，目前約 95% 的資料庫系統以它為基礎；競爭者有物件導向、物件關聯、XML、JSON 資料模型。

術語意思
表頭 header ＝ 關聯綱要 relational schema屬性名稱的序列
列 row（tuple）屬性值的序列；一列代表一組屬性之間的關係

  • 為什麼叫「關聯式」？Codd 原始定義：資料表是笛卡兒積 dom(A1) × … × dom(An) 的子集合，數學上這叫 relation。但這定義不完全對：兩張欄位順序不同的表資訊相同，兩個 domain 順序不同的 relation 卻不同。
  • 正確定義：一列 r 是完整的映射 r: {A1, …, An} → dom(A1) ∪ … ∪ dom(An)，且 r(A) ∈ dom(A)；資料表是列的集合。這樣欄位順序就無關緊要了。

D7.3 鍵

R(A1, …, An) 的鍵是屬性集合 K，滿足：(1) K ⊆ {A1, …, An}；(2) 任兩列在 K 上的值不同；(3) K 的任何真子集都不滿足 (2)。只滿足 (1)(2) 的叫 superkey；三條都滿足的叫 minimal key。

「鍵之國」導覽
minimal key = 最小的鍵；superkey = minimal key ＋其他屬性；candidate key = 任何一個 minimal key；primary key = 選中的那個 candidate key；foreign key = 參考另一張（或同一張）表的 primary / candidate key 的屬性集合。

1. SQL 語言總覽

🌍 什麼時候會用到：不管是網站後台、App，還是公司內部系統，只要背後有資料庫，開發者跟資料分析師幾乎每天都在寫 SQL — 從查會員資料、產生報表，到修改商品庫存，都要靠它。

2. 資料定義語言 DDL — CREATE / ALTER / DROP TABLE

🌍 什麼時候會用到：工程師要上線一個新功能（例如「願望清單」）之前，通常要先用 CREATE TABLE 設計一張新的資料表來存放這個功能的資料；日後需求變了要加欄位，就用 ALTER TABLE。

DDL 語句用來定義資料表的結構：有哪些欄位、每個欄位是什麼型別、有什麼限制條件。

CREATE TABLE DEPARTMENT( name VARCHAR(50) NOT NULL, code CHAR(5) NOT NULL, total_staff_number DECIMAL(2) NOT NULL, chair VARCHAR(50) NULL, budget DECIMAL(9,1) NOT NULL, CONSTRAINT dept_pkey PRIMARY KEY(name), CONSTRAINT dept_ckey1 UNIQUE(code) );

常見的欄位型別：VARCHAR(size) 變動長度字串、CHAR(size) 固定長度字串、INTEGER 整數、DECIMAL(M,D) 精確位數的數字、DATE / TIME / DATETIME 日期時間。

第二張表加上 FOREIGN KEY，讓它的每一列只能參照真的存在的系名稱 — ON DELETE CASCADE 則代表刪掉一個系時，這個系開的課也會自動被一起刪掉。

CREATE TABLE COURSE( cnum CHAR(7) NOT NULL, title VARCHAR(200) NOT NULL, credits DECIMAL(2) NOT NULL, offered_by VARCHAR(50) NULL, CONSTRAINT course_pkey PRIMARY KEY(cnum), CONSTRAINT course_check1 CHECK (credits IN (6, 12)), CONSTRAINT course_fkey1 FOREIGN KEY(offered_by) REFERENCES DEPARTMENT(name) ON DELETE CASCADE );
常見錯誤：DROP TABLE 的順序錯了 — 因為 COURSE 有一個外鍵指向 DEPARTMENT，MySQL 會拒絕先刪 DEPARTMENT：
DROP TABLE DEPARTMENT; -- ERROR 1217 (23000): Cannot delete or update a parent -- row: a foreign key constraint fails DROP TABLE COURSE; DROP TABLE DEPARTMENT; -- this order works: drop the child table (COURSE) first

ALTER TABLE 用來變更既有資料表的定義：新增或刪除欄位、改型別、新增或刪除限制條件、幫資料表改名。DROP TABLE 則會把整張表連同資料一起永久刪除。

ALTER TABLE DEPARTMENT ADD COLUMN category VARCHAR(20); ALTER TABLE DEPARTMENT DROP COLUMN budget; ALTER TABLE DEPARTMENT MODIFY code CHAR(6) NOT NULL; ALTER TABLE DEPARTMENT ADD CONSTRAINT dept_check2 CHECK (code = UPPER(code)); ALTER TABLE COURSE DROP FOREIGN KEY course_fkey1; ALTER TABLE DEPARTMENT DROP PRIMARY KEY; ALTER TABLE DEPARTMENT RENAME TO NEWDEPARTMENT;

用 ALTER TABLE 加限制條件 — 最容易翻車的四個地方

假設 PAYMENT 資料表有一個 Fee（費用）欄位，規定「必須大於 0、且不超過 9999.99」。要把這個規則寫成限制條件，最容易在下面四個地方出錯：

① DECIMAL(p, s) 的精度算對

DECIMAL(p, s) 裡，p 是「總位數」、s 是「小數位數」，所以整數部分能用的位數 = p − s。要存 9999.99（整數 4 位＋小數 2 位）就要寫 DECIMAL(6, 2)，不是 DECIMAL(4, 2)。

欄位型別整數位數（p − s）最大能存的值
DECIMAL(4,2)299.99
DECIMAL(6,2)49999.99
DECIMAL(9,1)899999999.9

最後一列就是本頁 DEPARTMENT.budget 的型別 — DECIMAL(9,1)。

✗ DECIMAL(4,2) 上限只到 99.99，9999.99 存不進去
ALTER TABLE PAYMENT MODIFY Fee DECIMAL(4,2) NOT NULL;
✓ DECIMAL(6,2)：整數 4 位＋小數 2 位
ALTER TABLE PAYMENT MODIFY Fee DECIMAL(6,2) NOT NULL;

② MODIFY 只能改欄位「型別」，不能寫條件式

MODIFY 是用來重新定義欄位的型別（以及 NULL / NOT NULL）。「大於 0 且小於等於某個值」這種是「條件」，要用 ADD CONSTRAINT 加一條 CHECK 限制。

✗ MODIFY 後面不能直接接條件式
ALTER TABLE PAYMENT MODIFY Fee > 0 AND Fee <= 9999.99;
✓ 型別交給 MODIFY，條件交給 ADD CONSTRAINT ... CHECK
ALTER TABLE PAYMENT MODIFY Fee DECIMAL(6,2) NOT NULL; ALTER TABLE PAYMENT ADD CONSTRAINT fee_range CHECK (Fee > 0 AND Fee <= 9999.99);

③ CHECK 裡的條件要寫完整，包含欄位名

每一個比較都要有「比較的對象」：欄位名在左邊、接運算符號、再接數值。兩個比較之間用 AND（或 OR）連接，不是用逗號。

✗ 缺少比較對象，SQL 看不懂
ALTER TABLE PAYMENT ADD CONSTRAINT fee_range CHECK (>0, <9999.99);
✓ 欄位名 ＋ 比較符號 ＋ 數值，再用 AND 連起來
ALTER TABLE PAYMENT ADD CONSTRAINT fee_range CHECK (Fee > 0 AND Fee <= 9999.99);

④ 邊界判斷：「不超過 X」要用小於等於

「不超過 9999.99」代表 9999.99 本身也是合法的值。如果用嚴格的「小於」，剛好等於 9999.99 的合法資料會被誤擋掉。看到題目的說法時，照下表選符號：

題目說法符號X 本身合法嗎？
大於 X>不合法
至少 X>=合法
小於 X<不合法
不超過 X（最多 X）<=合法
✗ 用 < 會誤擋掉剛好等於 9999.99 的合法值
ALTER TABLE PAYMENT ADD CONSTRAINT fee_range CHECK (Fee > 0 AND Fee < 9999.99);
✓ 不超過 → 小於等於 <=
ALTER TABLE PAYMENT ADD CONSTRAINT fee_range CHECK (Fee > 0 AND Fee <= 9999.99);
全部合起來： 先用 MODIFY 把型別改對，確保欄位真的存得下 9999.99；再用一條 ADD CONSTRAINT ... CHECK 寫完整的條件。
ALTER TABLE PAYMENT MODIFY Fee DECIMAL(6,2) NOT NULL; ALTER TABLE PAYMENT ADD CONSTRAINT fee_range CHECK (Fee > 0 AND Fee <= 9999.99);

3. 資料操作語言 DML — INSERT / UPDATE / DELETE

🌍 什麼時候會用到：使用者在網站上「註冊帳號」，背後其實是執行一次 INSERT；「修改個人資料」是 UPDATE；「刪除一則留言」是 DELETE。你每天滑手機做的操作，幾乎都會變成某一句 DML。

INSERT 新增一列，UPDATE 修改符合條件的列，DELETE 刪除符合條件的列。這三個在 COMMIT 之前都能用 ROLLBACK 復原 — 但它們都不會把資料表本身刪掉。

DELETE — 幾種挑列的方式

DELETE FROM COURSE WHERE cnum = 'CSCI235'; DELETE FROM COURSE WHERE (credits = 12) OR (UPPER(title) LIKE '%DATABASE%'); DELETE FROM DEPARTMENT WHERE total_staff_number < 5; DELETE FROM DEPARTMENT;

最後一行 — 沒有 WHERE 的 DELETE — 會刪掉每一列，但表本身還在（這跟把整張表刪掉的 DROP TABLE 不一樣，也跟速度更快、但不能 ROLLBACK 的 TRUNCATE 不一樣）。

常見錯誤：DELETE 的順序錯了 — 刪除一個還有課程的系會失敗，除非外鍵有宣告 ON DELETE CASCADE：
DELETE FROM DEPARTMENT WHERE name = 'Physics'; -- ERROR 1451 (23000): Cannot delete or update a parent -- row: a foreign key constraint fails DELETE FROM COURSE WHERE offered_by = 'Physics'; DELETE FROM DEPARTMENT WHERE name = 'Physics'; -- this order works: delete the child rows (COURSE) first

INSERT — 有沒有指定欄位清單

INSERT INTO DEPARTMENT VALUES ('Computer Science', 'CSCI', 30, 'Peter', 123456.9); INSERT INTO DEPARTMENT(name, code, chair, budget, total_staff_number) VALUES ('Mathematics', 'MATH', NULL, 12345.6, 10);
不指定欄位清單的 INSERT，值的順序必須跟資料表欄位順序完全一樣。明確列出欄位清單 — INSERT INTO T(col1,col2) VALUES(...) — 就可以跳過某些欄位（會變成 NULL）或改變順序。
常見錯誤：INSERT 的順序錯了 — 在系所還不存在之前先插入它的課，會違反外鍵檢查：
INSERT INTO COURSE VALUES ('PHYS999', 'Relativity II', 6, 'Physics'); -- ERROR 1452 (23000): Cannot add or update a child row: -- a foreign key constraint fails -- (fix: insert the 'Physics' department row first)

UPDATE — 改一欄、改好幾欄，或整張表都改

SELECT 敘述的子句永遠照這個順序排列，這個順序不能亂，也是新手最容易寫錯的地方：

記憶方式：先決定資料從哪來(FROM)，再篩選單一列(WHERE)，然後分組(GROUP BY)，對整組再篩一次(HAVING)，最後才排序(ORDER BY)。

16.1 Inline view — 括號裡的 SELECT 當成一張暫時的表

Inline view 是把一個 SELECT 用 ( ) 包起來，在右括號後面接一個名字（別名），並放在 FROM 或 JOIN 後面，也就是資料表名稱的位置。它只在這句查詢執行的期間存在。

判斷是不是 inline view，三個條件要同時成立：括號裡是一個 SELECT、右括號後面有別名、位置在 FROM 或 JOIN 之後。別名不能省略，MySQL 和 SQL Server 沒有別名會直接報錯。

17. 進階 DDL / DML

🌍 什麼時候會用到：季末要把「這一季的訂單」全部封存到另一張歷史資料表，可以用 CREATE TABLE ... AS 或 INSERT INTO ... SELECT 一次搬過去；清空一張「暫存匯入資料」的表格，用 TRUNCATE 比一筆一筆 DELETE 快得多。

這一章把前面學的 DDL / DML 跟 SELECT 子查詢接在一起：把「查詢結果直接寫進資料表」（CREATE TABLE ... AS、INSERT ... SELECT）、把「查詢結果當成刪除 / 更新的條件或新值」（DELETE、UPDATE 裡的子查詢），再加上一個快速清空資料表的 TRUNCATE。

19. 自主存取控制 — 使用者、權限與角色

🌍 什麼時候會用到：新來的助教只能看成績、不能改；會計系統可以新增訂單但不能刪；實習生離職要把權限全部收回；一百個客服人員要有一模一樣的權限 — 這些都是「誰可以對哪些資料做什麼」的問題，靠的就是 GRANT、REVOKE 和角色。

19.7 角色 — 一組有名字的權限

假設 James 要能讀 ITEM、寫 ORDERS；之後 Kate 也要一樣的權限 — 每多一個人就要把兩句 GRANT 再打一次。一百個人就是兩百句，而且哪天要多給一個權限，又要改一百次。

-- 講義的例子（ITEM、ORDERS、DISCOUNT 是講義的資料表） CREATE ROLE CUSTOMER; GRANT SELECT ON ITEM TO CUSTOMER; GRANT INSERT, UPDATE, DELETE ON ORDERS TO CUSTOMER; GRANT CUSTOMER TO James; GRANT CUSTOMER TO Kate; -- 角色可以再授予給角色，形成階層 CREATE ROLE FREQUENT_CUSTOMER; GRANT INSERT, UPDATE, DELETE ON DISCOUNT TO FREQUENT_CUSTOMER; GRANT CUSTOMER TO FREQUENT_CUSTOMER; GRANT FREQUENT_CUSTOMER TO Harry;
  • 角色本身就是一組權限：先把權限給角色，再把角色給使用者。之後修改角色的權限，所有拿到這個角色的人都會跟著變。
  • 角色可以授予給另一個角色：FREQUENT_CUSTOMER 擁有 CUSTOMER 的全部權限，再加上 DISCOUNT 的寫入權。CUSTOMER 有任何改動，FREQUENT_CUSTOMER 也會繼承。

20.2 交易是什麼？

交易（transaction）是對資料庫項目的一組 read、write 操作，而且這些操作有部分順序（partially ordered）。一個交易可以是一整個程式、程式的一部分、好幾句 SQL，或只是一句 SQL。

交易處理的基本原則：

  • 使用者透過執行程式跟資料庫互動；執行一個程式，就等於執行一組有部分順序的 read、write 操作。
  • 對交易來說，資料庫就是一堆資料項目（data items），寫成 x、y、u、v …（可以想成某一列或某個值）。
  • 同時執行的交易，操作會交錯（interleave）在一起。
  • 交易彼此不溝通，也不會影響其他交易的操作怎麼被處理。
  • 每個交易最後都以 commit（提交）或 abort（中止，又叫 rollback）結束。
  • 交易開始時資料庫是一致的，結束時也必須讓資料庫保持一致。

一個交易一生會經過的狀態：

交易執行中是 Active；做完最後一個操作進入 Partially committed，等確定變更都安全寫下才算 Committed。中途出錯（或寫入時失敗）就進入 Failed，接著把它做過的變更全部撤銷，成為 Aborted。

所有交易都要滿足四個基本性質，合稱 ACID：

Atomicity 原子性交易不可分割：要嘛全部做完，要嘛完全沒做不會出現「A 扣了錢、B 沒加到」

20.4 排程：序列與非序列

  • 排程（schedule）：同時執行的一組交易，實際被處理的順序；每個交易自己內部的操作順序必須保持不變。
  • 序列排程（serial schedule）：交易一個做完才換下一個，完全不交錯。
  • 非序列排程（nonserial schedule）：交易的操作交錯在一起。

20.5 可序列化 — 什麼樣的交錯是正確的

view serializable：如果一個非序列排程跟某個序列排程產生一樣的結果，而且每個交易讀到的資料都一樣，它就是正確的。問題是：判斷一個排程是不是 view serializable 是 NP-complete — 需要的時間會隨著交易數量呈指數成長，資料庫不可能每次都這樣檢查。

21.3 兩階段鎖定協定（2PL）

每個交易要存取資料項目之前，要先對它上鎖 lock(x)，用完再 unlock(x)；別的交易已經鎖住的項目，就只能等待。2PL 的原則：每個交易必須先取得所有的鎖，才能釋放任何一個鎖。所以每個交易分成兩個階段：只拿鎖的「成長階段」，和只放鎖的「縮減階段」。遵守 2PL 的排程一定是 conflict serializable。

  • 問題 1：死結（deadlock） — 兩個交易互相等對方手上的鎖。
  • 問題 2：沒必要的鎖 — 就算排程本來就是 conflict serializable，還是得上鎖、等待。

21.5 時間戳記排序協定（TO）

  • 原則：每個交易開始時拿到一個時間戳記（越晚開始越大）。交易每次讀或寫資料項目，就在項目上蓋上自己的時間戳記；存取必須照時間戳記由小到大的順序。年紀大（時間戳記小）的交易，如果要存取一個已經被年輕交易用過的項目，就太晚了 — 中止。
  • 精確地說，每個項目記錄 read_TS（讀過它的最大時間戳記）和 write_TS（最後寫它的時間戳記）：讀要求 自己 ≥ write_TS；寫要求 自己 ≥ read_TS 而且 ≥ write_TS。兩個讀不衝突，所以讀不會因為別人讀過而被中止。
  • 問題：連帶中止；以及沒必要的中止 — 就算排程其實是 conflict serializable，順序跟時間戳記不一樣也會被中止。TO 不用鎖，所以不會有死結。

讀到還沒 COMMIT 的資料。T2 把 budget 加 1000（未提交），T1 讀到 3000，接著 T2 ROLLBACK — T1 讀到的 3000 從來沒真正存在過。

不可重複讀 Non-repeatable read

同一個交易讀同一筆資料兩次，結果不同。T1 讀到 2000；T2 加 1000 並 COMMIT；T1 再讀變 3000。

幻影 Phantom

同一個交易同一個查詢兩次，取回的列集合不同。T1 數到 20 個系；T2 刪掉 SALES 並 COMMIT；T1 再數變 19。

差別一句話

不可重複讀是「同一列的值變了」（UPDATE）；幻影是「列的集合變了」（INSERT / DELETE 讓列冒出來或消失）。

② READ COMMITTED → 讀不到未提交的值，但提交後就讀得到（不可重複讀）

1SELECT budget … ; → 700.0

③ READ COMMITTED → 兩個交易改同一列：後來的要等（寫入會上鎖，避免遺失更新）

#T1T2
1UPDATE … budget = budget + 100 …;
2UPDATE … budget = budget + 100 …; Wait …
3SELECT budget …; → 800.0
4COMMIT;（取得鎖，執行 UPDATE）
5SELECT budget …; → 900.0 ; COMMIT;

如果先動手的那個交易 ROLLBACK，等待的那一方就以原本的值為基礎繼續：T2 加 50 後 ROLLBACK，T1 的加 100 結果是 800。

④ READ COMMITTED 仍會「弄壞」資料庫：T1 想把 SCIT 的 budget 設成跟 FIN 一樣（700），讀 FIN 後寫入；T2 把 FIN 加 50 並 COMMIT；T1 再根據 FIN 的新值計算另一個更新 → 同一個交易裡用到了兩個不同版本的 FIN，結果不一致（講義：Database is corrupted）。這就是不可重複讀造成的錯。

⑤ 死結（Deadlock）：T1 更新 FIN、T2 更新 SCIT；T1 再更新 SCIT → 等 T2；T2 再更新 FIN → 等 T1 → 互相等。MySQL 偵測到後回報 ERROR 1213 (40001): Deadlock found when trying to get lock; try restarting transaction，其中一方被迫 ROLLBACK，另一方可以 COMMIT。

⑥ REPEATABLE READ：T1 讀 SCIT = 100；T2 加 50 並 COMMIT；T1 再讀還是 100（看到的是交易開始時的快照）。

⑦ SERIALIZABLE：如果 SERIALIZABLE 交易 T 想更新或刪除「某個在 T 開始之後才提交的交易改過的資料」，系統就中止 T（Oracle：ORA-08177: can't serialize access for this transaction）。失敗後可以：(1) 提交目前已完成的部分、(2) 改執行其他敘述、(3) 整個 ROLLBACK。讀取方面，T 會看到交易開始時的版本：別人提交了新版本（例如 Sales 加 50），T 讀到的仍是 700。

考試陷阱：題目問「這個時間軸在哪個最低等級下不會出問題」：有讀到未提交的值 → 至少 READ COMMITTED；同一列讀兩次值不同 → 至少 REPEATABLE READ；COUNT 或範圍查詢的列數變了 → 只有 SERIALIZABLE。

22. 資料完整性 — 一致性限制、COMMIT / ROLLBACK、備份與還原

🌍 什麼時候會用到：學號重複、課程掛在一個不存在的系底下、一次刪到一半的資料被別人看到、硬碟壞掉整個資料庫不見 — 這些都是「資料完整性」出問題。這一章看資料庫用哪些方法防止資料被意外改壞，以及壞了之後怎麼救回來。

22.1 資料完整性是什麼？

  • 資料完整性（data integrity）指的是資料整體的完整、正確與一致：兩次更新之間資料沒有被意外改變，資料保持原樣。
  • 它要在資料的整個生命週期都維持住，所以是任何儲存、處理、讀取資料的系統在設計、實作和使用時都必須考慮的事。
  • 它的反面是資料損毀（data corruption），也就是一種資料遺失。
  • 所有完整性技術的目的都一樣：資料寫進去時跟原本想寫的完全一樣，之後讀出來時也跟當初寫進去的一樣。一句話：防止資訊被非預期地改變。

這一章的三個工具各自守住一部分：一致性限制擋掉不合規則的資料；COMMIT / ROLLBACK 確保別人不會看到改到一半的資料；備份與還原在資料真的不見時把它救回來。

22.2 一致性限制

一致性限制（consistency constraint）是資料庫所模擬的那部分真實世界裡「永遠成立」的性質，也就是資料庫每一個持久狀態都必須滿足的條件。例如：學號唯一識別每個學生、小型研究計畫的預算不能超過 10K、生日可以是未知、每個員工剛好屬於一個系、正教授的薪水在某個範圍內。

22.4 ROLLBACK、COMMIT 與 AUTOCOMMIT

  • ROLLBACK 立刻撤銷最近的修改：上一次 COMMIT（或連線開始）之後做的所有修改都會被撤銷。
  • COMMIT 把上一次 COMMIT（或連線開始）之後的所有修改變成永久的，之後再也不能用 ROLLBACK 撤銷。
  • 系統變數 AUTOCOMMIT 控制什麼時候變成永久：OFF 時要等到 COMMIT、或任何 DDL（CREATE、ALTER、DROP）才提交；ON 時每一句 DML 執行完就自動提交。
  • 每個連線開始時 AUTOCOMMIT 預設是 ON；跟其他系統變數一樣用 SET autocommit = 0; 修改（第 18 章）。
  • EXIT 不會提交：AUTOCOMMIT = OFF 時沒 COMMIT 就離開，那些修改會被撤銷。

講義的例子：要把一個系整個刪掉，得先刪它開的所有課，再刪系本身 — 兩句 DELETE。如果 AUTOCOMMIT = ON，第一句一執行就提交了；這時另一個使用者來查，就會看到一個「還存在、卻一門課都沒開」的系 — 這是錯的資訊。講義刪的是 Arts，本筆記的資料換成 Physics：

23. 正規化 — 函數相依、鍵、1NF / 2NF / 3NF / BCNF

🌍 什麼時候會用到：設計資料表時，一張表塞太多東西，就會出現「改一個地址要改一百列」、「沒有零件就記不了倉庫」、「刪掉最後一個零件，倉庫地址也跟著不見」這些問題。正規化就是一套檢查與拆表的規則，判斷一張表設計得好不好、不好的話要怎麼拆。考試最常考：找鍵、判斷最高達到哪個正規化形式、拆成 3NF / BCNF。

整理自 CSIT882 第 5–7 週講義。考前只看 23.1 速查區和 23.2 常錯區；23.3 參考區把完整範例收起來，需要時再點開。

23.2 常錯區

錯誤寫法正確寫法原因
① 漏找 candidate key：找到 AB 是鍵就停下來先找沒出現在任何 FD 右邊的屬性，再逐一加入其他屬性算 closure，每個組合都試完漏一個鍵就漏掉 prime 屬性，後面 2NF / 3NF 全部判錯（練習 6 的 AC 就很容易漏）
② 把 key 和 prime 混為一談：「B 是 prime，所以 B 是鍵」prime 是「至少屬於一個 candidate key 的單一屬性」；key 是一組屬性，要用 closure 證明3NF 的例外看的是「右邊是不是 prime」，不是「右邊是不是 key」
③ BCNF 寫成「左邊是 prime 就 OK」BCNF：左邊必須是 superkey（X⁺ = R）prime 只是某個鍵的一部分，決定不了全部屬性
④ BCNF 把左邊看成右邊：「右邊 B 是 prime，所以符合 BCNF」BCNF 只看左邊是不是 superkey，右邊是什麼都不影響「右邊是 prime」是 3NF 的例外，BCNF 沒有例外
⑤ 3NF 例外條款用錯：左邊不是 superkey 就直接判違反 3NF；或把「或右邊是 prime」搬去判 BCNF3NF：左邊是 superkey 或右邊是 prime；BCNF：只有左邊是 superkey 這一條這條例外正是 3NF 和 BCNF 唯一的差別（Location、Teaching、練習 6）
⑥ 2NF 把「key 的一部分決定 prime」當違規：「C 是 AC 的一部分，C → B，違反 2NF」2NF 只管 nonprime：key 的真子集決定 nonprime 才違反 2NF；決定 prime 不違反 2NF（可能只違反 BCNF）2NF 的定義是「每個 nonprime 屬性完全相依於鍵」，prime 屬性不在檢查範圍
⑦ 各級結論互相矛盾：寫「不滿足 2NF」又寫「滿足 3NF」；或最高 NF 寫 3NF，BCNF 那段卻寫滿足BCNF ⊂ 3NF ⊂ 2NF ⊂ 1NF：從 2NF 往上判，第一個不滿足的就停，最高 NF 是最後一個滿足的不滿足 2NF 就不可能滿足 3NF；寫完要逐行對照最後一句
⑧ 「是 superkey」沒附證據：寫「AB is a superkey」或「AB = {A, B, C, D}」寫出 closure：AB⁺ = {A, B, C, D} = R, so AB is a superkey.closure 就是證據，沒寫會被扣分；漏了 ⁺ 意思就變成「AB 這個集合等於全部屬性」，是錯的

函數相依 FD 與 Armstrong 公理

X → Y（讀作「X 決定 Y」或「Y 函數相依於 X」）：在這張表裡，不可能有兩列 X 的值一樣、Y 的值卻不一樣。換句話說，知道 X 的值，就最多只對得到一個 Y 的值。

講義的例子FD為什麼
每個倉庫只有一個地址warehouse → warehouse-address知道倉庫就知道地址
同一個倉庫裡，同一種零件只有一個總數量warehouse, part → quantity要兩個一起才決定得了
每個供應商住在一個城市supplier → city
一家公司不一定只在一個城市company → city 不成立同一家公司可以對到好幾個城市
  • FD 來自資料的意義（需求規格、常識），不是來自某一刻的資料內容。
  • 範例資料只能推翻 FD（找到兩列 X 一樣、Y 不一樣），不能證明 FD — 現在剛好沒有反例，不代表以後不會有。

推導 FD：從已知的 FD 可以推出新的 FD。最基本的三條是 Armstrong 公理，其他規則都能從它們推出來：

規則寫法白話
反身律 reflexivity若 Y ⊆ X，則 X → Y自己決定自己的一部分：a, b → a

正規化分析器練習 6：R(A, B, C, D)

👀 看解答

A 沒出現在右邊，所以每個鍵都有 A；A⁺ = {A} 不夠。AB⁺ = {A, B, C, D} = R，AC⁺ = {A, C, B, D} = R，AD⁺ = {A, D} 不是 → 鍵是 AB 和 AC。Prime：A、B、C；Nonprime：D。C → B：C⁺ = {B, C} ≠ R，但 B 是 prime → 只違反 BCNF（也不違反 2NF，因為 B 不是 nonprime）→ 最高 3NF。拆到 BCNF 得到 (B, C) 和 (A, C, D)，但 AB → C、AB → D 會失去。

軟體缺陷（約 35% 成功攻擊）開發時有意或無意寫進程式：設計瑕疵（設計決策本身就不安全）與程式錯誤（一般 bug、沒想清楚後果的功能、緩衝區溢位、競爭條件、後門、不夠隨機的亂數產生器）。
組態錯誤（約 65% 弱點）開了不必要又危險的服務、允許不需要的連線；通常是因為用廠商「全部開啟」的預設組態安裝，而不是只開需要的功能。
存取管理錯誤群組、角色、權限、委派很複雜，設定一錯整個安全模型就垮；而且很難偵測，因為從外部看存取「看起來是合法的」。

S1.3 SQL Injection

應用程式手上有資料庫連線，用字串串接把固定的 SQL 片段跟使用者輸入拼起來送給伺服器。攻擊者故意輸入畸形資料，讓 SQL 從無害變成惡意 — 未授權存取、刪資料、竊取資訊。根本原因永遠是應用程式的 bug。

sqlString = "SELECT USERID FROM USER WHERE USERID = '" & userID & "' AND PWD = '" & pwd & "'"; result = GetQueryResult(sqlString); if (result = "") then userHasBeenAuthenticated = False else userHasBeenAuthenticated = True

講義的輸入讓 WHERE 變成 USERID = '' OR '' = '' AND PWD = '' OR '' = ''：空字串等於空字串是 TRUE，OR 讓整個條件為 TRUE，結果不是空的 → 被當成登入成功。

補充：怎麼防（講義沒列，但一定會用到）：用參數化查詢 / prepared statement，讓使用者輸入永遠只是「值」不是「程式碼」；驗證輸入；應用程式帳號只給最小權限（第 19 章）；不要把資料庫錯誤訊息直接顯示給使用者。

S1.4 資料庫木馬（Trojan）

  • 木馬：藏在合法程式裡的未授權程式 — 看起來做一件事，背地裡做別的事（名稱來自特洛伊木馬的神話）。
  • 資料庫木馬分兩階段：注入惡意程式碼、呼叫惡意程式碼。兩個階段看起來不相關，所以很難追蹤；注入後可能潛伏很久（sleeper）才被啟動。
  • 四種類型：(1) 攻擊者自己注入也自己呼叫；(2) 利用不知情的使用者 / 程序注入，攻擊者呼叫；(3) 攻擊者注入，不知情的使用者 / 程序呼叫；(4) 注入和呼叫都由不知情者完成。例：初階開發者從陌生人那裡拿到 trigger 或 stored procedure，不懂內容就直接用。

S1.5 消除弱點、強化 MySQL

對付木馬

追蹤 stored procedure 的執行：建立基準線（baseline）、監控偏離、記錄並分析 log、即時警示、能比對基準線的防火牆；控管 procedure / trigger 的建立與修改；注意 run-as 權限的變動；嚴密監控開發者在正式環境的活動；監控 trace 與 event monitor 的建立；小心 email 裡的 SQL 附件。

強化 MySQL

實體保護伺服器；local_infile='OFF'（停用 LOAD DATA LOCAL）；skip_show_database（SHOW DATABASES 只列有權限的）；secure_auth='ON'；skip-name-resolve='ON'（只用 IP 不解析主機名）；不給非管理者 PROCESS、FILE、SUPER；MySQL 不要跟 Web 伺服器放同一台；root 用強密碼；取消本機使用者預設全權和遠端預設連線；不用 4.1 以前的版本；限制 load_file；開發者不能碰正式資料庫；開啟稽核。

S2. 資料庫稽核 — 稽核什麼、MySQL 的各種 log

🌍 什麼時候會用到：出事後要回答「誰、什麼時候、從哪裡、做了什麼」；金融業還要能證明資料沒被竄改。考題常問「下列情境要稽核哪一類活動」或「哪個 log 記錄什麼」。

S2.1 概念

  • 資料庫稽核（database auditing）：觀察資料庫，掌握使用者的動作；通常為了安全，例如確保沒權限的人沒有存取資訊。
  • DAM（Database Activity Monitoring）：獨立於 DBMS 的監控技術，不依賴 DBMS 內建稽核或 trace、交易 log；通常即時、持續進行。
  • 稽核軌跡（audit trail / audit log）：DAM 的產出 — 依時間排列、與安全相關的紀錄，作為某項操作或事件發生經過的書面證據。

做法：MySQL Enterprise Audit（社群版沒有；可動態開關、依政策記錄登入或查詢、依大小輪替 log、XML 格式整合第三方）、stored procedure、trigger、外部稽核外掛、分析資料庫 log。

Log記錄什麼
Error log伺服器啟動、停止、執行時的嚴重錯誤；位置由 log_error 決定
General query log建立的客戶端連線與收到的所有敘述；general_log 開關，log_output = FILE 或 TABLE（mysql.general_log）

S3. 資料隱私 — 統計資料庫、推論攻擊、隨機化、k-匿名

🌍 什麼時候會用到：醫療、普查、成績資料只開放「統計查詢」（COUNT、AVG……），但巧妙組合幾個統計查詢，就能反推出某個人的資料。考題常給一串查詢結果，要你算出個人值或說明是哪種攻擊。

S3.1 信任與私密資訊檢索

  • 信任（trust）：一方（trustor）願意依賴另一方（trustee）的行為。系統裡，「A 信任 B」表示 B 的性質被破壞時，A 的正確運作可能受影響。值得信任（trustworthiness）：能被依賴去做該做的事；trustworthy computing：本質上安全、可用、可靠的系統。
  • 私密資訊檢索（PIR）：查詢資料庫但隱藏「取回了哪些項目」— 就像在店裡買東西而店員不知道誰買了什麼。應用：醫療、個人、電子商務資料庫、網路搜尋。

S3.2 統計資料庫與推論

統計資料庫：每列是一個人，個別資料敏感不能直接讀，只允許對某欄做聚合查詢（COUNT、SUM、AVG、MAX、MIN）。例：STUDENT(name, sex, degree, units, ave_grade)，可以問 BCompSci 的平均成績，但不能讀個人的 units 和 ave_grade。

  • 聚合（aggregation）：聚合結果的敏感度跟個別值不同 — 通常較低（AVG(salary)），但也可能更高（SUM(expenses) 可能透露整體機密）。
  • 推論問題（inference problem）：從不敏感的資料推導出敏感資訊。
攻擊做法
直接攻擊在很小的樣本上算聚合，洩漏個人值
間接攻擊組合多個聚合的資訊
追蹤者攻擊用條件鎖定單一列
線性系統弱點用查詢集合之間的代數關係列方程式，解出個人值
例 1：直接攻擊

Carol 是 BCompSci 的女學生。先問 SELECT COUNT(*) FROM STUDENTS WHERE sex = 'F' AND degree = 'BCompSci';，如果答案是 1，再問同條件的 AVG(ave_grade) — 得到的「平均」就是 Carol 本人的成績。能鎖定單一列的條件叫個人追蹤者（individual tracker，又稱 quasi-identifier）；能拿來回答任何不被允許的查詢的條件叫一般追蹤者（general tracker）。

例 2：追蹤者 — 算出 Carol 的學分
SELECT SUM(units) FROM STUDENTS WHERE name = 'Carol' OR degree = 'MIS'; -- 75 SELECT SUM(units) FROM STUDENTS WHERE name = 'Carol' OR NOT (degree = 'MIS'); -- 77 SELECT SUM(units) FROM STUDENTS; -- 136
Carol 的學分是多少？

(75 + 77) − 136 = 16。前兩個查詢加起來，所有學生都被算了一次，只有 Carol 被算了兩次（她同時滿足兩個條件裡的 name = 'Carol'）；減掉全體總和就剩 Carol。

例 3：連「拒絕回答」都會洩密

sum(x1, x2, x3) = 15；接著問 max(x1, x2, x3) 被系統拒絕。max 一定 ≥ 5（不然總和到不了 15）；如果 max > 5，回答它也推不出任何個別值，系統沒理由拒絕；唯一合理拒絕的情況是 max = 5 → 推出 x1 = x2 = x3 = 5，三個值全部外洩。

方法做法弱點

S4. 資料管理的法律與倫理議題

🌍 什麼時候會用到：DBA 能讀寫所有機密與歷史資料，所以法規和倫理特別重要。考題多是申論：「合法一定合乎倫理嗎？」、「某法規對資料管理有什麼要求？」、「專利、著作權、商標差在哪？」

S4.1 兩難與倫理

  • DBA 的兩難來自：能不受限地讀寫機密、有價值的資訊與歷史資訊。
  • 為什麼要談倫理：從業人員的品行；專業與不專業的行為；犯罪組織取得資料的壓力；電子化的敏感資料越來越多、能接觸的人越來越廣。
  • 倫理（ethics）：正確行為的一組原則，或道德價值的理論 / 體系。
  • 不倫理行為例子：安裝盜版軟體、存取個人資訊、洩漏商業機密（約 57% IT 人員曾被要求這樣做）、讀寫資料探勘與資料倉儲的歷史分析結果。
問題答案
不倫理的行為都違法嗎？不是：不是所有行為都有法律規範
合乎倫理的行為都合法嗎？不是：存在法律漏洞
